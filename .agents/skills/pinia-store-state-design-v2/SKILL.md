# Piniaストア状態管理詳細設計

Vue / Piniaの現行実装を調査し、ストアの定義、画面操作ごとのストア変更、参照、状態遷移、横断処理、設計上の所見を1つの設計書にまとめる。アプリケーションコードは変更しない。既存仕様や一般的な実装から動作を推測せず、実装で確認できた事実、既存テストで検証済みの事実、未確認事項を区別する。

この設計書の読者は「ストアを追加・変更する人」と「画面を追加する人」である。前者は定義・依存・リセット経路を、後者は自分の画面が触るべきストアと横断処理を知りたい。両者が表を眺めて答えにたどり着けることを目標にし、同じ情報を何度も繰り返す表より、固有の情報だけが残る短い表を優先する。

## 1. 対象と出力先

1. 指定されたプロジェクト・画面・ストアを対象とする。指定がなければプロジェクト全体のPiniaストアと画面を対象とする。対象外の状態（画面ローカル、Cookie、サーバー状態など）は本文に明記する。
2. 対象プロジェクトの文書配置・命名・更新規則を確認する。出力先の指定があればそれに従い、なければ既存の詳細設計の配置に合わせる。適切な既存の配置がなければ `docs/store-state-design.md` とする。ファイル名は文書名（状態管理設計）と対応させ、調査レポート向けの名前（`*-report.md` など）と混同しない。既存の関連資料は内容を確認して更新し、無関係な文書は上書きしない。文書一覧・フォルダ構成・リンクの同時更新がプロジェクトで必要な場合は合わせて行う。
3. `pinia-store-usage-survey`（または `-v2`）の成果物（`store-usage-report.md`、`store-usage.csv`）が既にあれば読み、アクセス明細・違反候補・確度をこの設計書の入力に使う。ただし実装が更新されていれば明細を鵜呑みにせず、差分を確認する。
4. 調査した実装、静的調査か実行検証済みかを明記する。実行していない動作は実行検証済みと書かない。既存の単体テスト・E2Eテストが検証している振る舞いは「テスト済み」として区別し、テスト名を参照できるようにする。

## 2. 実装を追跡する

対象内の全画面・ストアを列挙し、それぞれ次の経路を最後まで追う。全画面の初期表示を確認し、何も変更しない画面も一覧に含める。

- **ストア定義**：`defineStore`、Options Store / Setup Storeの別、state（型・初期値）、getter、action、reset / clear（Setup Storeに `$reset` はなく、手書きの関数が代替になる）、直接代入、他ストアへの呼び出しを確認する。Setup Store内でreturnされないローカル変数（進行中要求のMap、世代カウンタ、AbortControllerなど）はstateに含まれない内部状態として別に記録する。devtoolsにもテストの観測対象にも現れないため、設計書に書かなければ存在が伝わらない。永続化プラグイン、ブラウザー保存領域との同期・復元があれば、保持と破棄の範囲を確認する。
- **画面・共通処理**：ルーター、ガード、共通レイアウト、画面、子コンポーネント、composable、watch、ライフサイクルをたどる。ボタン、フォーム、タブ、画面初期表示、パラメーター変更、画面離脱、ログイン・ログアウトなど、実際に存在する起点に紐付ける。
- **参照**：テンプレート、computed、watch、ガード、ハンドラ内でストアのstate・getterを読む箇所を、画面・共通処理ごとに集める。参照は変更に比べて量が多いので、画面×ストア単位に「どのstate / getterを読むか」までで十分とし、箇所の列挙はしない。
- **非同期・API**：画面やストアからAPIクライアント、共通インターセプターまでたどり、HTTPメソッドと実際のパス、条件付きの呼び出しや後続APIを確認する。ストア自体のAPIと、同じ画面操作内で別の処理が呼ぶAPIを区別する。
- **分岐**：成功・失敗・キャンセル・認証切れ、入力検証、キャッシュ、同時要求、破棄後の応答、画面離脱・再表示を確認する。各分岐の対象と発生条件を特定する。
- **横断処理**：ガードやインターセプターのような共通コードに加えて、各画面に同じ形で複製されている処理（401検知でストアを破棄してログインへ戻す、など）も横断処理として扱う。実装上は画面ごとでも振る舞いが同一なら、設計上は1つの規則である。適用範囲（どの操作に適用されるか）と、適用されない例外を画面単位で特定する。
- **既存テスト**：ストアやAPIクライアントのテストを探し、どの分岐・条件を検証しているかを記録する。実行できる環境なら実行し、結果を記録する。
- **その他の起点**：タイマー、ブラウザーイベント、WebSocketなど、画面操作以外にストアを変更する起点があれば漏らさず別途記載する。

共通コンポーネントやストア間の呼び出しは実際の利用元までたどり、画面への波及を確認する。動的な参照などで追跡できなかった経路は「不明」とし、確認できた範囲と理由を残す。

## 3. 資料を作成する

次の構成を基本とし、対象プロジェクトの実装に応じて項目を増減する。

### 3.1 対象と読み方

- 対象範囲、対象外の状態、調査方法（静的／実行／テスト）を書く。
- 表の用語を定義する。**設定**は未保持（`null`・空・未定義）の値に初めて値を入れること、**更新**は既に保持している値を置き換える・部分変更すること、**クリア**は初期値に戻すこと、**なし**は変更もAPI呼び出しもないこと。既定でこの基準を使い、プロジェクトの実装で区別が付かない場合は「設定／更新」を1語にまとめてよい。どちらにしても採用した基準を本文に書く。基準が書かれていないと、同じ代入が行によって設定になったり更新になったりして読者が意味を探し始める。
- 対応API列は画面操作に関連して呼ばれるAPIであり、必ずしもストア自身による呼び出しではないと明記する。

### 3.2 ストア定義

ストアごとに次を表にする。ストアを追加・変更する人がここだけ読めば全体像を得られる粒度にする。

| 項目 | 内容 |
|---|---|
| 名前・ID | 識別しやすい名称と `defineStore` のID |
| 記法 | Options Store / Setup Store |
| state | キー、型、初期値、初期値の意味（例：`null` は未初期化、`{authenticated:false}` は未認証） |
| getter | 名前と導出元 |
| action | 名前、変更するstate、呼ぶAPI |
| 内部状態 | stateに含まれない変数とその役割 |
| 依存 | 呼び出す他ストアと、その呼び出しが起きるaction |
| 初期化・破棄 | 初期化の起点、クリア手段（`$reset` / 手書き関数）、破棄される契機 |
| 永続化 | プラグイン・保存領域の有無と範囲 |

記法が混在している、あるストアが別の機能ストアを知っている、といった事実はここで分かるようにし、評価は3.6に回す。

### 3.3 横断処理

画面に関係なく適用される変更・参照を先に1か所にまとめる。ルーターガード、共通ヘッダー、インターセプター、そして各画面に複製されている同一処理がここに入る。

| 処理 | 起点 | ストア | 対象 | 処理概要 | 対応API | 適用範囲・例外 |
|---|---|---|---|---|---|---|
| 認証状態の初期化 | 初回の画面遷移 | 認証（`auth`） | `user`、`initialized` | 設定 | `GET /api/auth/me` | 全画面。2回目以降は参照のみ |
| セッション切れ検知 | 認証必須APIの401 | 認証（`auth`） | `user` | 更新（未認証） | なし | APIを呼ぶ全操作。例外：ロール履歴取得は無視、ログインAPIの401はログイン失敗として扱う |

上の行は形式例であり、対象プロジェクトで実際に確認した内容に置き換える。

- 複数画面に同じ処理が複製されている場合、ここに1組だけ書き、画面別の表には書かない。画面別の表に同じ2行が画面数×操作数だけ並ぶと、画面固有の変更が埋もれて読めなくなる。
- 適用範囲は「APIを呼ぶ全操作」のように規則として書き、規則から外れる画面・操作は例外として必ず列挙する。例外を省くと、その画面を直す人が横断処理を前提にして誤る。
- 参照だけの横断処理（ガードがgetterを読んで遷移を決める、ヘッダーが表示名を読む）も1行ずつ載せる。変更の表には現れないが、getterを変えたときの影響先として必要になる。

### 3.4 画面操作とストア

画面固有の変更だけを載せる。横断処理に含めた変更は「3.3を参照」とし、繰り返さない。

| 画面 | イベント | ストア | 対象 | 処理概要 | 対応API |
|---|---|---|---|---|---|
| 商品詳細 | 初期表示 | 商品（`product`） | `current`（`open`） | クリア・設定 | `GET /api/products/{id}` |
| 商品詳細 | タブ押下 | 商品（`product`） | `tabs[tab]`（`load`） | 設定（未取得時） | `GET /api/products/{id}/tabs/{tab}` |
| 商品詳細 | 画面離脱 | 商品（`product`） | 全state（`clear`） | クリア | なし |
| 商品一覧 | 初期表示 | なし | なし | なし | `GET /api/products` |

上の行は形式例であり、対象プロジェクトで実際に確認した内容に置き換える。

- 画面は画面名、イベントは「初期表示」「検索ボタン押下」「タブ押下」「画面離脱」のような操作・ライフサイクルの粒度とする。ハンドラ名や内部実装のステップをイベント名にしない。
- 対象列には変更されるstateのキーと、経由するactionを括弧で書く。actionを経由しない直接代入は「（直接）」と書く。これで「何が」「どの経路で」変わるかが表だけで分かり、ストアを変更する人が影響を受ける行を検索できる。
- 原則1行1ストアとし、1操作で複数ストアが変わる場合は行を分ける。
- 変更のない初期表示も記載し、ストア参照のみなら対象・処理概要を「なし」とする。参照の内訳は3.5に書く。
- APIは `GET /path/{id}` の形式で列挙する。取得条件がある場合や操作途中で複数APIを呼ぶ場合も実際の経路を示す。APIを呼ばない場合は「なし」、調査で特定できない場合は「不明」とする。
- 処理概要は設定・更新・クリア・なしを組み合わせ、必要なときだけ「（成功時）」「（未取得時）」など短い条件を付ける。常に起きる変更に条件を付けない（例：エラー時にしか表示されない再試行ボタンは常に取得するので「（取得時）」は不要）。条件付きの変更を無条件に見せない。
- 表のセルは単語か短文に統一し、長い説明は3.7に置く。

### 3.5 参照マトリクス

画面・共通処理を行、ストアを列にし、セルに読むstate / getterを書く。変更しかしない場合は「W」、読み書き両方なら読む項目に「+W」を添える。

| 画面・共通処理 | 認証（`auth`） | 商品（`product`） |
|---|---|---|
| ルーターガード | `isAuthenticated`、`isAdmin` | – |
| 共通ヘッダー | `user.displayName`、`isAdmin`、+W | – |
| 商品詳細 | – | `current`、`tabs`、+W |

getterやstateの名前を変えるとき、どの画面を直すかをこの表で決められる。参照箇所の行番号までは書かない。

### 3.6 状態遷移と設計上の所見

**状態遷移**：status型の値（`loading` / `success` / `error` など）や、`null` と値で意味が変わるstateがあれば、遷移を表にする。

| 現在 | 契機 | 次 |
|---|---|---|
| 未取得 | `load` 開始 | `loading` |
| `loading` | 応答成功 | `success` |
| `loading` | 応答失敗（401以外） | `error` |
| `error` | 再試行 | `loading` |
| 任意 | `clear` | 未取得 |

**設計上の所見**：次の観点で実装を見て、該当する事実を短く列挙する。断定や修正はせず、意図的な設計の可能性があればそう書く。ここは「直すべき箇所の一覧」ではなく「ストアを増やす・変える人が知っておくべき癖」の一覧である。

- ストア外からの直接代入、`$patch`、破壊的メソッドによる変更
- `storeToRefs` を使わないstate / getterの分割代入
- ストアのstateへの直接 `v-model`
- 汎用コンポーネントや子コンポーネントからのストア変更
- ストア間の依存方向（認証ストアが機能ストアを知っている、循環している、など）と、新しいストアを追加したときに追記が必要になる箇所
- ログアウト・画面離脱・セッション切れでリセットされないストア
- 記法の混在（Options / Setup）
- actionの戻り値で画面に判断を委ねている契約（401を `boolean` で返す、など）
- 非リアクティブな内部状態の存在と、それがテスト・devtoolsから見えないこと

### 3.7 表に収まらない情報

表で正確に表せない場合に限り、対象の画面・イベント・ストアを特定して短く補足する。例えば更新の順序とタイミング、条件ごとのAPI、キャッシュの有無、同時要求の扱い、失敗時や破棄後の応答の扱い、永続化先、条件から外れる例外を記載する。各項目に検証状況を付ける：

| 補足 | 検証状況 |
|---|---|
| 取得済みのタブはAPIを呼ばず保持値を再利用する | テスト済み（`tests/product.test.ts`「cached tabs」） |
| 破棄後に完了した応答はストアに反映しない | テスト済み（同「late response」） |
| 401検知時は商品ストアをクリアした後に認証を未認証にする | 静的確認のみ |

実装にない共通ルールを作らず、表現できなかった点を明示する。

### 3.8 実装参照・調査の限界・更新規則

- 主要なストア・ルーター・共通処理・画面・APIクライアント・テストの実装へのリンクをまとめる。
- 動的な経路、条件、実行未検証などの限界は具体的に記載する。
- この文書を更新すべき契機を1〜2行で書く（例：ストア追加時は3.2と3.3のリセット経路、画面追加時は3.4と3.5、横断処理の例外が増えたときは3.3）。

## 4. 確認

- 実装上の全対象画面に初期表示行があり、関連操作・横断処理・画面以外の更新起点に漏れがない。
- 3.2の依存・内部状態・クリア手段が実装と一致し、3.3の適用範囲と例外が画面ごとに確認済みである。
- 横断処理に含めた変更が3.4に重複して並んでいない。逆に、横断処理から外れる画面固有の例外が3.3に列挙されている。
- 対象列にstateキーと経由actionがあり、設定・更新・クリアの条件、APIのメソッド・パス・呼び出し条件が実装と一致する。参照のみ、変更なし、未確認を区別する。
- 参照マトリクスに、ガード・共通コンポーネントを含む全参照元がある。
- 3.7の各項目に検証状況があり、既存テストで検証済みのものを「静的確認のみ」と書いていない。
- ファイル名が文書名と対応し、リンク先と文書配置規則を確認した。

完成後、出力先、対象範囲、横断処理としてまとめた規則と例外、設計上の所見、未確認事項を簡潔に報告する。
